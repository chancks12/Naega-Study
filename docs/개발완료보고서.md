## 2. 작업 항목 상세

### 2-1. 포즈 추출 공식 정렬 (학습 데이터와 일치)

**문제**  
학습 데이터 수집(`collect_data.py`, mediapipe 0.10.14)과 클라이언트 C++ 추출값 사이에 neck_angle 20° 이상, head_yaw 2× 스케일 오차가 발생하였다. AI 서버 모델이 학습 분포 밖의 입력을 수신하여 추론 결과가 왜곡되었다.

**원인 및 수정**

| 항목 | 기존 | 수정 후 |
|---|---|---|
| `neck_angle` | 양쪽 귀+어깨 평균 | 왼쪽 귀(7) + 왼쪽 어깨(11) 단독, `atan2(dx, dy)` |
| `head_yaw` | solvePnP 기반 3D 각도 | `(lm[454].x - lm[234].x) × 100 × crop_w / (192 × frame_w)` |
| `head_pitch` | solvePnP 결과 | `atan2(lm[152].y - lm[1].y, lm[152].x - lm[1].x) - 90°` |

`head_yaw`의 경우 Python 학습 코드는 전체 프레임 정규화 좌표 [0,1]을 사용하지만, C++ ONNX face_landmark 출력은 크롭 공간 [0,192] 좌표이므로 `crop_w / (192 × frame_w)` 보정 항이 필수이다.

**수정 파일**
- `client/src/analysis/LocalMediaPipePoseAnalyzer.cpp`
- `client/include/analysis/LocalMediaPipePoseAnalyzer.h`

### 2-2. ONNX Stride 버그 수정 (Shoulder 671° 문제)

**문제**  
Shoulder 값이 671.4°와 같은 비정상 수치를 출력하였다.

**원인**  
pose_landmark 모델 출력이 39×5 = 195 floats (랜드마크당 x, y, z, visibility, presence) 구조인데, `195 % 3 == 0` 조건으로 stride=3으로 잘못 판단하여 visibility/presence의 raw logit 값을 좌표값으로 혼용하였다.

**수정**  
stride 결정 우선순위를 `elem_count % 39 == 0` → `elem_count % 33 == 0` 순으로 변경하여 195를 stride=5로 올바르게 처리한다.

```cpp
if      (elem_count % 39 == 0) stride = static_cast<int>(elem_count / 39);
else if (elem_count % 33 == 0) stride = static_cast<int>(elem_count / 33);
```

추가로 stride ≥ 4인 경우 귀(7), 왼쪽 어깨(11), 오른쪽 어깨(12)의 visibility < 0.5이면 해당 프레임의 pose 결과를 무효 처리하여 배경 인물 오감지를 방지한다.

### 2-3. EMA 스무딩 적용

**문제**  
정적 자세에서도 neck_angle, shoulder_diff 수치가 프레임마다 크게 튀는 현상이 발생하였다.

**수정**  
- `neck_angle`, `shoulder_diff` 출력에 EMA (α=0.2) 적용 → 약 5프레임 평균 효과
- 초기 프레임(has_ema_ = false)은 EMA 초기값으로 바로 설정하여 스무딩 지연 없음
- face 미감지 시 EMA 상태 초기화하여 stale 값 잔류 방지

### 2-4. 이벤트 발화 빈도 제어

**문제**  
AI 서버 응답 전 로컬 상태(`focus → distracted → focus`)가 매 프레임 PostureEventDetector에 전달되어 이벤트가 폭주하였다.

**수정**
- AI 서버 미응답 상태에서는 `ev.state`를 비워 로컬 임계값 경로 사용
- 정상 상태(`focus`) 전환 시에만 cooldown 해제
- 최소 발화 간격 5,000ms 가드 추가: `last_event_ms_` 기준 5초 미만이면 `schedule_event` 무시

### 2-5. 프레임 전송 성능 최적화 (CPU 환경)

**문제**  
FPS 설정을 15로 하였음에도 AI 서버에 초당 8~10프레임만 도달하였다.

**원인 및 수정**

| 항목 | 원인 | 수정 |
|---|---|---|
| CaptureThread 이중 대기 | `capture >>` 블로킹 후 `sleep_for` 추가 대기 | `sleep_for` 제거 — 카메라 블로킹 읽기가 이미 프레임 레이트를 조절함 |
| 핫 패스 디버그 로그 | 프레임마다 `OutputDebugStringA` 문자열 생성 + 시스콜 | 핫 패스에서 제거 |

> CPU 환경에서 ONNX 추론이 80~120ms를 점유하는 것은 하드웨어 한계이며, 나머지 불필요한 오버헤드를 제거하여 가능한 최대 처리량을 달성하였다.

### 2-6. 공부 시작 이벤트 로그 추가

**요구사항**  
비정상 상태(졸음/자리비움/다른행동)에서 집중 상태로 복귀할 때 "공부 시작" 로그를 남겨 사용자가 집중 구간의 시작 시각을 확인할 수 있도록 한다.

- `LocalClaimCheckClipStore`: `"focus"` 폴더명으로 매핑
- `ClipsPanel`: 화면에 `"공부 시작"`으로 표시

### 2-7. 캘리브레이션 프로토콜 분리 (2002 / 2000)

**배경**  
AI 서버가 캘리브레이션 기준 데이터와 실제 추론 데이터를 구분할 수 있어야 한다.

**구현**

| protocol_no | 용도 |
|---|---|
| `2000` | 일반 추론 프레임 |
| `2001` | AI 서버 → 클라이언트 응답 |
| `2002` | 캘리브레이션 기준 프레임 |

- `AiTcpClient::set_calibration_mode(bool)` 추가
- `calibration_mode_` = true일 때 `send_keypoint_packet`에서 `protocol_no = 2002` 사용
- 캘리브레이션 중 수신한 AI 응답은 `last_result_` 업데이트에서 제외

**AI 서버 팀에 대한 요청사항**  
`protocol_no = 2002` 패킷은 캘리브레이션 기준 데이터이므로 추론에 사용하지 않고 기준값 계산에만 활용할 것. `protocol_no = 2000`부터 정상 추론을 시작할 것.

### 2-8. 캘리브레이션 방식 변경 (5초 타이머 → 150프레임 카운트)

**변경 전**: Windows 타이머(IDT_CALIB) 5초 카운트다운

**변경 후**: 150프레임 전송 완료 기준

**이유**  
CPU 환경에서 ONNX 추론 속도에 따라 5초 내 전송 가능한 프레임 수가 일정하지 않다. 프레임 수 기준으로 변경하면 실제 데이터량이 보장된다.

**구현 흐름**

```
[세션 시작]
    ↓
begin_calibration()
  - calibration_mode_ = true
  - on_calibration_complete 콜백 등록
  - 오버레이: countdown=1 (안내 메시지 표시)
    ↓
AiTcpClient::run() — 150프레임 protocol_no=2002 전송
    ↓
calib_frames_sent_ >= 150
  - calibration_mode_ = false
  - PostMessage(WM_CALIB_COMPLETE) → UI 스레드
    ↓
OnCalibrationComplete() → finish_calibration()
  - 오버레이: countdown=0 (완료 메시지 1.5초)
  - IDT_CALIB_HIDE 타이머 → countdown=-1 (오버레이 숨김)
  - 이후 protocol_no=2000 일반 프레임 전송 시작
```

**오버레이 메시지**

| 상태 | 메시지 |
|---|---|
| 캘리브레이션 진행 중 | 「공부 자세를 잡아주세요.」 / 「판단의 기준점이 됩니다.」 |
| 완료 | 「기준 자세가 설정되었습니다.」 / 「공부를 시작합니다.」 |

**수정 파일**
- `client/include/network/AiTcpClient.h`
- `client/src/network/AiTcpClient.cpp`
- `client/src/app/StudySyncClientView.cpp`
- `client/src/app/StudySyncClientView.h`
- `client/src/render/OverlayPainter.cpp`

### 2-10. Haar Cascade 단일 인물 포커스 로직 제거

**문제**  
다수의 얼굴이 감지될 때 가장 큰 얼굴을 선택하는 로직이 오히려 ONNX 모델의 추론을 방해할 수 있다고 판단하였다.

**제거된 코드**
- `cv::CascadeClassifier face_cascade_` — Haar 캐스케이드 분류기
- `cv::Rect2f ema_face_rect_` — 얼굴 박스 EMA 추적 상태
- `int haar_frame_count_` — 5프레임 간격 카운터
- `initialize()`의 cascade XML 로드 블록
- `analyze()`의 detectMultiScale + 최대 얼굴 선택 + EMA 갱신 섹션 전체
- `#include <opencv2/objdetect.hpp>`

**변경 후**  
크롭 영역을 프레임 중앙 절반 고정값으로 대체한다.

```cpp
const cv::Rect face_rect(W / 4, 0, W / 2, H / 2);
```

ONNX 모델이 직접 해당 영역에서 얼굴/포즈를 탐지하므로 별도의 사전 필터링이 불필요하다.

## 4. AI 서버 팀 협의 사항

### 캘리브레이션 프로토콜 처리

클라이언트는 세션 시작 시 **최초 150프레임**을 `protocol_no = 2002`로 전송한다.

- `protocol_no = 2002`: 캘리브레이션 기준 데이터 → **추론에 사용하지 말 것**, 기준값(baseline) 계산에만 활용
- `protocol_no = 2000`: 150프레임 이후 정상 추론 프레임 → 여기서부터 추론 시작

패킷 JSON 구조는 동일하며 `protocol_no` 필드값으로 구분한다.

```json
{
  "protocol_no": 2002,
  "session_id": 12345,
  "frame_id": 1,
  "timestamp_ms": 1234567890,
  "ear": 0.31,
  "neck_angle": 12.4,
  "shoulder_diff": 3.1,
  "head_yaw": 28.5,
  "head_pitch": -5.2,
  "face_detected": 1
}
```

| 항목 | 내용 |
|---|---|
| CPU 추론 속도 | ONNX CPU 추론 ~80-120ms/프레임으로 실질 전송 fps = 8~12. GPU 환경(CUDA/DirectML) 전환 시 개선 가능 |

| 캘리브레이션 데이터 활용 | AI 서버에서 2002 패킷을 기준값 계산에 활용하는 서버 측 구현 필요 |
